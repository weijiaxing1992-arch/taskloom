# TaskLoom 社区版容量与运行规划

## 能力边界

本版使用单个 Go 服务和本地 SQLite 保存业务数据，附件也会增加数据库及备份规模。当前没有可用于保证任意部署环境容量的公开生产基线；未经目标环境压测，不承诺固定并发人数、工作项上限、响应时间或恢复时间。自动化测试通过不能替代真实负载测量。

容量应根据活跃人数、同时编辑量、搜索、完整导出、附件大小和外部 AI 请求模式评估。相同需求数量可能因附件与评论体积产生完全不同的资源占用，不应只按成员数购买资源。

## 数据与磁盘预算

先在隔离环境导入合成样本，记录每类工作项和附件的增长量，再估算日常数据库、WAL、至少一次完整备份、保留历史快照和升级副本需要的空间。不要将样本估算当作已经验收的产品容量。

监控数据卷可用空间和增长趋势，备份应位于权限和故障域独立的位置。磁盘不足时不能直接删除 WAL、SHM 或当前数据库；先阻止进一步容量风险，再按维护流程取得一致性副本和调查长事务。过期备份的清理应按部署方批准的保留策略执行。

## 建议测量项目

对目标服务器测量登录、列表分页、中文检索、并发编辑、附件上传下载、完整需求导出和通知刷新。记录峰值请求数、P50/P95 延迟、错误比例、内存、CPU、磁盘 IO、数据库锁等待及备份耗时。手机端另测慢网下正文、代码和附件加载，界面流畅度不能仅由服务端均值推断。

验证失败、取消、项目切换和身份失效时的行为；没有数据与缺失估算不能展示成零工作量。压测只对合成数据和独立环境执行，真实业务库不适合作为破坏性测试目标。

## 告警、备份与扩展

部署方需要独立健康探测、磁盘与错误告警、备份失败通知及恢复演练。内置服务器监控仅为管理员可读的当前快照，不提供自动扩容或站外值班服务。备份频率、保留期、允许数据损失和恢复时限应由业务确认并通过实测修正。

单机服务存在单点风险；异地备份提供恢复手段，不是自动高可用。不要把多个服务副本直接指向同一 SQLite 文件来增加容量。跨节点扩展需要单独设计数据存储、会话、限流和通知任务协调，并重新验证所有权限与一致性边界。
